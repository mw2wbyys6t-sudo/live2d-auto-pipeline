# 安全审计 → 核实 → 分级修复 → 验证闭环

本技能固化一套经过多轮实战的代码安全工作流，适用于 Python + Go + TypeScript 混合栈。
核心信条：**扫描结果一律不信任，核实后才动手；修复必须有真实行为证据；推送必须看 CI 全矩阵。**

## 何时使用

- 用户要求「检查代码是否有潜在问题」「安全审计」「修复 P0/P1/P2」
- 依赖升级 / CVE 排查 / 密钥泄露检查 / CORS 配置 / 子进程超时加固
- 日志脱敏、凭据存储、注入面检查

不适用于：单纯功能开发、纯格式重构（无安全面）、已在运行的安全事件应急（走 incident 流程）。

---

## 阶段一：多维度并行审计

用并行子代理同时扫描，避免串行浪费时间。固定维度清单：

1. **密钥与凭据**：硬编码 key/token/password；`__repr__`/`toString`/日志/CLI 是否泄露密钥片段；脱敏是否覆盖所有日志级别（而非仅遥测/结构化数据路径）
2. **网络安全**：CORS（`*` + credentials 是致命组合）；`verify=False`；绑定地址
3. **依赖 CVE**：requirements / go.mod / package.json 的版本下限
4. **进程与资源**：subprocess/exec.Command 无超时；文件句柄无上下文管理器；HTTP 连接无复用
5. **错误处理**：`except: pass` 静默吞异常（区分业务逻辑 / 资源清理 / best-effort 降级）
6. **注入面**：shell=True、eval/exec、pickle.load、SQL 拼接、yaml.load
7. **代码卫生**：未使用导入、重复常量/映射、死代码、TODO/FIXME

扫描产物必须带：**文件路径 + 行号 + 代码片段 + 问题描述**，不允许只给结论。

## 阶段二：核实（本技能最关键的一步）

扫描器（grep/子代理/依赖数据库）会产生大量误报。每条 P0/P1 必须核实后才进入修复：

### 2.1 CVE 必须查权威源核实，禁止照抄扫描结论

- 查 NVD（nvd.nist.gov）和 GitHub Security Advisory，确认：
  - **受影响包到底是谁**（例：ReDoS 公告常同时列出框架名与实际的解析库，真正要升级的是底层库）
  - **真实修复版本号**（例：目录遍历在 3.9.2 而非 3.9.5；某 CVE 在项目当前下限版本中已修复，则该项取消）
  - **项目是否真的使用了受影响的代码路径**（例：静态目录遍历只在开启特定选项时可利用）
- 查不到可靠公告的「漏洞」标注为存疑，不升级、不写进修复清单
- 核实结论要写进提交信息（哪些升级、哪些误报被纠正、为什么）

### 2.2 源码复核每条「缺陷」

- 打开调用点读上下文。已有保护机制的不算问题（例：启动流程已用 timer+kill 实现就绪超时）
- 长驻进程（服务器、桌面宠物、watch 循环）**禁止加 timeout**——这是特性不是缺陷；应改为补信号处理（Ctrl+C）和非零退出码提示
- 一次性命令（pip install、构建、模型下载、环境探测、健康检查）才需要超时

### 2.3 分级标准

- **P0**：可直接利用的凭据泄露 / 密钥进环境变量或版本库 / RCE 注入
- **P1**：危险默认配置（CORS 通配符+凭据）、已知 CVE 版本下限、可导致永久挂起的无超时调用
- **P2**：信息泄露面（日志脱敏不全、repr 泄露尾号）、静默吞业务异常、重复代码
- **P3**：最佳实践（with 语句、连接池、冗余依赖）

## 阶段三：修复约定

### 3.1 通用原则

- 安全默认值 + 环境变量可覆盖；覆盖解析要处理无效值（回退默认并告警）；约定 `0 = 不限制`
- 超时默认值按场景给足：交互式探测 15-60s，业务调用跟现有配置预算走，安装/大包下载 30-60 分钟
- 超时触发后要杀进程并给出**可操作的提示**（如何调大上限、如何重试），退出码可对齐 POSIX `timeout` 的 124
- 同一策略在多语言/多入口间保持一致（例：Python 降级服务的 CORS 白名单默认值必须与 Go 主服务相同）
- 错误信息不泄露内部路径/堆栈给外部客户端，但服务端日志要保留详情
- 修主路径时，同步修「兜底/回退路径」里的同类硬编码（例：requirements 安装失败后的逐个安装包列表）
- 正则/拦截类修复要同时写**正向用例**（该拦的拦住）和**负向用例**（正常文本不误伤，如 `token_count=` 不是密钥）

### 3.2 各语言速查

- **Python subprocess**：`subprocess.run(..., timeout=N)`，捕获 `TimeoutExpired`；`Popen` 长驻进程配 `terminate()`/`kill()` 清理
- **Go**：`exec.CommandContext(ctx, ...)` + `context.WithTimeout`，用 `ctx.Err() == context.DeadlineExceeded` 区分超时与执行失败；参照文件内已有的标准模式，不要自创
- **FastAPI/Starlette CORS**：白名单 list；`["*"]` 时必须 `allow_credentials=False`（CORS 规范硬性要求）
- **日志脱敏**：在 Formatter 层拦截（覆盖所有级别和所有 handler），不要只在业务调用点脱敏

## 阶段四：多层验证（每层都要真实证据）

1. **语法/编译**：Python `python -m py_compile <所有改动文件>`；Go `go vet ./... && go build ./...`
2. **现有测试**：跑受影响包的测试；沙箱缺依赖导致的失败，先补装依赖复跑确认是环境问题而非回归
3. **真实行为测试（必须做，不能只靠读代码）**：
   - CORS：用框架真实的中间件 + TestClient 发请求，断言恶意来源**无** ACAO 头、白名单来源有头且带 credentials、预检 OPTIONS 同样受控、通配符模式无 credentials 头
   - 超时：真实拉起 `sleep` 进程，断言在超时值附近被杀（而不是等满）
   - 脱敏：真实走 logger 管道输出，断言密钥不出现在格式化后的文本中
4. **配置测试**：默认值、环境变量覆盖、`0=不限`、非法值回退，四个分支都测
5. 全部通过标准：`N passed, 0 failed`，失败数为零才算完成

## 阶段五：提交与 CI 闭环

- 提交信息写清：问题、修复、**核实依据**、验证命令与结果；纠正的误报也要记录
- 推送后用 CI 工具查看 run，**逐个 job 核对**（不要只看总结论）：测试矩阵的每个语言版本、构建、打包、Docker
- 注意 workflow 的触发条件差异：push/PR 触发的 job 与 schedule/workflow_dispatch 触发的 job 可能有不同的依赖安装步骤——一个全绿不代表另一个没问题
- 定时任务失败要翻失败 job 的完整日志找根因（常见：某 job 的依赖列表与主 job 漂移）；没有手动触发权限时，给出修复依据（同环境已验证 + 主 job 同款配置）并说明何时自动验证
- CI 全绿后再向用户汇报完成；任何红项必须说明根因和后续

## 汇报格式

- 按 P0→P3 列表，每项：文件链接:行号、问题一句话、修复一句话
- 单列「误报纠正」小节，体现核实价值
- 给出验证证据摘要（测试数、CI job 数）
- 范围外发现的独立问题单独列出并询问是否处理，不擅自扩大改动范围

## 红线

- 不盲信任何扫描器/子代理/CVE 数据库的结论，无权威核实不动版本号
- 不给长驻服务加超时
- 不在用户未确认时提交/推送之外做额外重构
- 不把密钥、内部 URL、一次性运行 ID 等写进可复用产物
