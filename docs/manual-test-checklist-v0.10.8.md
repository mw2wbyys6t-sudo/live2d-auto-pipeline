## 2. 状态机（对应"卡在 Checking... / 显示 Offline"）

| # | 检查点 | 期望 | 结果 |
|---|---|---|---|
| B1 | 启动后的状态检查 | 几秒内完成并进入正常界面，**不停在 "Checking..."** | ☐ 通过 ☐ 失败 |
| B2 | 连接状态显示 | 显示在线 / 正常，**不显示 "Offline"** | ☐ 通过 ☐ 失败 |
| B3 | 关闭应用里依赖的本地服务后再启动 | 状态能正确反映，不误报也不卡死 | ☐ 通过 ☐ 失败 |

> 失败特征（B 组）：永久停在 "Checking..."；明明服务已就绪却显示 "Offline"

> **本次补充修复（Offline 误报根因）**：连接指示器原先用 `/api/health` 的
> `res.ok` 判断，而该端点在后端可达、仅缺少**可选** Python 依赖（PIL/numpy）时
> 会返回 **503** —— 于是「后端正常但弱依赖缺失」被误判成整体 `Offline`。
> 现改为：**只要收到任何 HTTP 响应即视为后端可达**（网络不可达才判 `Offline`）；
> 缺依赖的具体信息仍由 `/health` 环境自检页与 `/api/status` 呈现。
> 涉及文件：`web/lib/api-client.ts` 的 `healthCheck()`。
