## 1. 决策问题（Decision Question — Rev.2 修订版）

面向开源发布与二创生态，本项目应采用何种开源协议，才能同时满足：

1. **保留原作者产权** — 源代码、算法、角色形象、视觉资产等全部原始成果的知识产权不被剥夺；
2. **允许他人非商业性创作/二创** — 个人、社团、教育场景可自由修改、分发、衍生；
3. **防止商业盗用** — 他人不得将本项目及衍生作品包装为付费产品/SaaS/付费模型商城/企业生产工具；
4. **（Rev.2 新增）加严约束** — 防止二创作者将衍生作品切换至更宽松的 3.0/4.0 协议从而变相商用；强制二创注明**具体修改内容与日期**；要求**每一份再分发副本都带 License 全文/URI**；禁止施加 DRM 或额外技术限制。

## 4. 决策（Decision）

**采用 CC BY-NC 4.0（知识共享 署名-非商业性使用 4.0 国际）作为本项目唯一许可协议。**

协议同时覆盖：源代码、配置文件、文档、AI 管线设计、角色形象生成算法、视觉资产、Live2D 绑定模板等全部项目产出。

## 5. 后果（Consequences）

### 正面 ✅
- 商用路径被**显式且合法地**切断（F3）。
- 二创/教学/社区场景完全保留，不会像 GPL 那样吓跑用户（F2）。
- 署名条款是"硬约束"，GitHub fork、二次分发、打包为桌面 App 时都必须保留 Live2D Master Agent Team 署名（F1）。
- 与 `docs/CODE_STANDARD.md` 中的贡献流程一致，外部 PR 天然署名归项目所有（合并即同意协议）。

### 负面 / 缓解 ⚠️
- **NC 灰色地带**：如"用户用本项目生成的 Live2D 角色去接稿约稿/直播带货收益"，严格说不属于"对本作品本身的商业使用"，属于使用者对**自己生成的衍生形象**的处置。已在 README 许可证章节用"（包括但不限于付费下载、广告变现、售卖 Live2D 模型、付费 SaaS 服务、企业内部商业生产等）"举例限定，只覆盖"对本项目代码/管线的直接商用包装"。
- **无法收取许可费**：商用被禁止后，项目商业化只能靠"商用授权例外（Dual License）"——保留团队另行向付费客户发放商用 License 的权利（这是 CC BY-NC 天然允许的，版权所有者不受 NC 约束）。
- **企业贡献门槛略升**：大厂员工贡献需先过内部法务确认 NC 无冲突 → 缓解：README 提供联系通道。

# 📌 Revision 2 — 2026-07-30 修订：CC BY-NC 4.0 → **CC BY-NC 2.0 Generic**（降级，加严约束）

> 本节为 Rev.2 单独决策记录。Rev.1 原 4.0 的上下文、备选、后果等仍保留于上半部分，仅用于记录决策沿革，不构成现行约束。

## R2-1. 修订决策问题

原 CC BY-NC 4.0 国际版存在的宽松点，与产权所有者的真实诉求存在偏差：

1. 4.0 允许衍生作品"兼容至 BY-SA 4.0 / GPL 等"，给变相降级留了空间；
2. 4.0 "注明更改"只要求"说明做了更改"，不要求写清具体改了什么；
3. 4.0 "标注许可"只要求提供链接，不要求每一份副本都**附带协议 URI / 文本**；
4. 4.0 对"商业使用"的判定对「企业内部使用」「间接获益」的定义较模糊。

产权所有者决定**加严**（即"降到" 2.0 版本，约束更多、被许可方活动空间更小）。

# 📌 Revision 3 — 2026-07-30 当晚修订：CC BY-NC 2.0 → **MIT**（恢复 v9.0 原版许可，现行生效）

> 本节为 Rev.3 单独决策记录。Rev.1 / Rev.2 仍保留于上文，仅用于记录决策沿革与历史版本发布的合法性，不构成现行约束。

## R3-1. 修订决策问题

Rev.2 的 CC BY-NC 2.0 虽然在"保护产权、防止商用盗用"层面非常理想，但经过产权所有者当日下午至晚间的评估，存在以下 4 个**根本性与工程代码类项目不兼容**的问题：

1. **NC 条款定义模糊 → 贡献门槛过高**：企业开发者（如大厂员工、自由职业者、做外包的团队）的法务基本都会拒绝 NC 协议，哪怕只是"业余时间贡献代码"，导致社区贡献者池大幅缩小；
2. **与代码类资产不匹配**：CC 协议（BY-NC）是为**艺术作品、文档、图片、音乐**等创作类资产设计的，对"源代码、算法、API 接口"这类工程资产的兼容性很差（CC 官方也**不推荐**用 CC BY-NC 许可代码）；
3. **生态兼容性差**：MIT / Apache-2.0 / GPL / BSD 等标准代码开源协议都**无法与 CC BY-NC 2.0 混并**，导致任何想把本项目代码片段或模块融入更大的工程栈（哪怕是开源的）的行为都涉嫌违规；
4. **与 v9.0 用户预期相悖**：v9.0 用户的使用体验是"最宽松的 MIT"，v10.0 直接切到 BY-NC 2.0 属于破坏性变更，社区可能因此大规模迁移或 Fork。

产权所有者决定**恢复 v9.0 原版 MIT 协议**（Rev.3）。

## R3-2. 修订推动力（新增 Forces Rev.3）

| 推动力 | 说明 |
|--------|------|
| F9 · 代码类项目的生态预期 | 绝大多数 AI / 开源工具项目（Stable Diffusion WebUI、ComfyUI、VTube Studio 开源组件等）都用 MIT/Apache-2.0。用户下载本项目后，默认预期是能自由用于任何场景（包括商用赚钱）。 |
| F10 · 外部贡献者激励 | NC 协议下，有价值的代码贡献者（比如写 Go API、调 Live2D Cubism SDK、做 Docker 打包）的贡献意愿接近零——因为他们无法在自己的商业项目里复用自己写的代码。MIT 下贡献者保留自己的代码权利，激励更高。 |
| F11 · 与 v9.0 承诺的一致性 | README 顶部的 v9.0 vs v10.0 对比表中未列出任何"许可证升级为更严格协议"的破坏性变更条目。MIT 是 v9.0 原版状态，恢复它即兑现承诺。 |
| F12 · 产权所有者自身的商业自由 | 虽然版权所有者理论上不受 NC 条款约束，但在法律文件中声明 NC 可能会影响未来寻求投资、企业合作、SAAS 化服务的法务尽调（需反复解释"所有者不受约束"）。MIT 下没有这种歧义。 |

## R3-3. 修订备选对比

| 方案 | 描述 | 结论 |
|------|------|------|
| A · 保持 Rev.2 CC BY-NC 2.0 | 最严格的产权保护；但 F9-F12 四条力全败 | ❌ 不推荐，与工程代码类项目生态冲突 |
| B · 切到 CC BY 4.0（仅保留署名） | 允许商用但必须署名；仍属于 CC 协议家族，与代码资产兼容性仍不理想，且工程贡献体验仍差于 MIT | ❌ 次优，未解决"CC 协议不适用于代码"的根本问题 |
| C · 切到 Apache-2.0 | 优秀的代码类协议（含专利授权条款）；但 v9.0 原版是 MIT，用户预期是"MIT 级别的宽松"；专利条款对小项目意义不大 | ❌ 过度设计，与"恢复 v9.0"目标不符 |
| D · **MIT（恢复 v9.0 原版，当前修订）** | OSI 官方认可的最宽松代码开源协议之一；一条义务（保留版权+许可声明）；允许任何用途（商用、修改、分发、再许可、闭源）；与代码资产 100% 兼容；与 v9.0 用户预期完全一致；社区贡献门槛归零 | ✅ 选定（符合"恢复 9.0 版本许可"诉求） |
| E · 自制"保留署名+允许商用"协议 | 自制协议不具备 OSI 认可，开源平台不识别，法律不可执行 | ❌ 红线，禁止 |

## R3-4. 修订决策

**现行主分支协议 = MIT License（恢复 v9.0 原版，Rev.3 现行）。**

- Rev.1 历史版本（commit `418e071` 之前）：仍按 CC BY-NC 4.0 永久有效（版权所有者不得撤销已发放许可）。
- Rev.2 历史版本（commit `9b6c4a1` ～ `65fb3b4` 之间发布）：仍按 CC BY-NC 2.0 永久有效（不追溯）。
- 自本次 Rev.3 commit（PR #6 合并后新的 HEAD）起，**所有新提交与新发布产物一律按 MIT 发布**。

## R3-5. 修订后果

### 正面（Rev.3 比 Rev.2 更符合工程代码类项目生态）
- **商业化自由度拉满**：MIT 允许任何用户/企业用在闭源商业产品、付费 SaaS、付费定制、企业内部生产工具里，不需要告知原作者，不会触发任何法律风险 → F9/F12 命中。
- **社区贡献门槛归零**：开发者（包括大厂员工、自由职业者、团队）可以放心提交 PR，也可以在自己的商业项目里复用自己贡献的代码 → F10 命中。
- **与 v9.0 承诺一致**：README 的 v9.0→v10.0 升级对比表没有"许可破坏性变更"，用户体验是连续的 → F11 命中。
- **协议兼容性最强**：MIT 代码可自由并入任何更大的工程栈（Apache-2.0、GPL、BSD、闭源、商业产品都 OK），无 CC 家族与代码类协议混并的法律障碍。
- **法律文本精简、全球通用**：MIT 全文仅 3 段，无翻译歧义；中国、美国、欧盟法院均有成熟判例，法律风险最低。
- **保护产权仍然存在**：MIT 协议虽然宽松，但**"保留版权+许可声明"是一条刚性义务**，任何商用/再分发都必须把 MIT 全文放进每一份副本里 → 原作者的"署名与所有权"通过版权声明的方式被永久保留（区别于"放弃版权"的公共领域）。

### 负面 / 缓解
- **商用盗用风险"理论上升"**：理论上有人可以把本项目打包成"AI Live2D 生成器 Pro"直接卖钱、不加任何感谢或回报。缓解措施 4 条：
  1. **保留独家品牌护城河**："Live2D Master Agent Team"作为品牌名受商标法保护，盗用者**不能冒用我们的品牌**（MIT 只授权代码，不授权商标/品牌）；
  2. **社区口碑效应**：真正的商用客户通常会优先找**原作者团队**做定制/支持/SLA，而不会买匿名盗用的 fork；
  3. **随时切换回严格协议的权利保留**：版权所有者随时可以对**未来版本**切换到 Dual License（开源 MIT + 商业付费版），历史版本不追溯（即"免费先发、后期商业化"路线）；
  4. **项目官网 / 文档署名**：MIT 保留的版权声明（Copyright (c) 2026 Live2D Master Agent Team）在每一份副本中永久存在，形成事实上的"软署名"——任何盗用产品的合规部门/法务都能溯源到原作者。
- **（潜在）代码被闭源商业项目"白嫖"不回馈**：这是宽松协议的通病（所有 MIT/Apache-2.0 项目都面临）。缓解：优先打造**文档/生态/社区**作为护城河（这部分闭源公司抄不走），而非单靠代码保密。
