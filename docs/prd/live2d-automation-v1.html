Product Requirements Document · v1

Live2D 角色自动化制作：素材分层与绑定规格

把一张角色原画变成「结构合理、可导入 Live2D Cubism、能继续绑定和做动画」的分层素材， 并同时产出网格、变形器、参数、物理的规格与验收证据。素材分层完成与 模型绑定完成在本产品中是两个独立状态，各自要求不同的证据。

深度 Heavy · 新工作流 主用户 Live2D 绑定师 交付形态 PSD + 规格包 + 验收报告 状态 待评审

1. 背景与目标

当前链路已经能把原画切成 29 个语义图层，并算出每个部件的像素网格、关节拆分与覆盖率 （实测一张 600×900 立绘：37 个绑定部件、12509 顶点、119812 个角色像素 100% 被网格覆盖）。 但产出的东西无法直接交给 Live2D 继续做，原因不在分层质量，而在交接形态：

问题一：交接物不是 Cubism 能吃的格式

现在交付的是 PNG 图层包与 JSON。Cubism 的官方入口只有一个： 导入 PSD 自动生成 ArtMesh。PNG 包无法代入层级、无法保留坐标原点、 无法让绑定师在 Editor 里继续工作。

问题二：「分层好了」被误读成「模型能动了」

分层完成只说明图被切开了。模型能不能动取决于网格密度、变形器层级、参数键形与物理， 这些是另一套工作。两者混为一谈，就会把「切图成功」当成「模型可交付」。

决定性约束：Cubism 没有可编程的建模接口 官方「外部应用集成 API」的全部指令是：注册插件、读取/写入参数值、读取参数与参数组、 读取文档与当前模型、读取当前编辑模式、读取物理 FPS、写日志，以及四类导出完成通知 （NotifyMocFileExported / NotifyPhysicsFileExported / NotifyMotionFileExported / NotifyMotionSyncFileExported）。 没有任何指令能创建 ArtMesh、设置网格顶点、创建变形器、创建参数或关键形状，也没有保存工程文件的指令。 参见 官方指令表。 官方 Core 只提供读取 .moc3 的接口，.cmo3 是 Editor 的工程格式且无公开规范（见 文件类型 与 Core API）。

由此得到一个必须写进产品契约的结论：「一键生成 Live2D 可编辑工程」在官方路径上不成立。 产品的真实价值点不是伪造这一步，而是把「导入前」的一切做到可导入、可校验、可继续绑定， 并把「导入后」的剩余工作显式交出去。

目标（可观测）

  • 绑定师拿到的 PSD 能被 Cubism Editor 一次导入成功，图层结构直接映射成部件树，不出现导入报错或图层丢失。
  • 每个部件都带有网格规格（顶点/三角形/覆盖率），绑定师可以选择沿用或替换自动生成的网格。
  • 每份交付都附带状态与证据：哪些是机器已验证的、哪些需要人工签核、哪些没做——三者不混写。

2. 产品契约与能力边界

这是本 PRD 最重要的部分。下面的边界决定了产品能承诺什么，也决定了验收怎么判。

能力归属说明与依据
原画分析、部件规划、分割、遮挡补绘 产品负责 可直接产出并逐像素验收。
构建符合 Cubism 硬约束的导入用 PSD 产品负责 硬约束见 §5 FR-04，全部来自官方「PSD 创建注意事项」。
产出网格 / 变形器 / 参数 / 物理的规格文件 产品负责 规格可机器校验（顶点是否落在部件上、覆盖率、父子关系是否成环）。
生成 physics3.json 产品负责 物理配置是运行时文件，不依赖 Editor 编辑态，可直接生成并校验。
在 Cubism Editor 内创建 ArtMesh / 变形器 / 键形 产品不负责 官方无对应 API（见上方约束）。导入时 Editor 自动生成「最少顶点 + 1px 内边距」的 ArtMesh，此为官方行为，与产品无关。
输出 .cmo3 可编辑工程 不承诺 无公开格式规范、无官方写入接口。任何此类产物都属逆向实现，不得作为默认交付物宣传。
「模型能动了」的判定 条件成立 仅在「已通过官方内核加载 + 参数变化产生预期形变 + 人工观感签核」三项齐备时才成立，见 §6 证据等级。
推论：网格规格的真实用途 产品算出的像素网格在官方路径上有三个合法用途：① 作为绑定师替换自动网格时的目标规格； ② 作为自检依据（对比 Editor 自动生成的网格密度是否够用）； ③ 若走自建 .moc3 编译链路，则作为该链路的输入。 它不是「导入即生效」的东西，交付文案不得这样描述。

3. 范围

P0：最小完整旅程

原画→ 分层计划→ 分割 + 补绘→ 画布组装→ 导入用 PSD→ PSD 自检→ 人工导入 Cubism→ 绑定规格→ 验收报告

入口条件：用户提供一张角色原画（含透明通道或可分离背景）。
完成证据：一份可被 Cubism 导入的 PSD + 规格包 + 验收报告，报告中每一层都能追溯到「已验证 / 待签核 / 未做」。

最重要的失败恢复：PSD 导入失败。产品必须在交付前自己先做一次「重开 + 图层结构 + 合成比对」， 把会因为「同名图层、图层蒙版、非 8bit、非 sRGB、线稿未合并」而被 Editor 拒绝或改色的问题挡在交付之前。

P1：可选增强

  • 参数键形与网格键形的自动烘焙（依赖自建 .moc3 编译链路，且须先解决已知内核崩溃问题）。
  • 眼白/瞳孔/高光/上下睫毛的进一步细分，以及嘴型多态（mouth_a/i/u/e/o）。
  • 多视角设定图（正面/侧面/背面）驱动同一套部件的形变参考。

明确不做

  • 不做「导入 Editor 后自动完成建模」的宣称或暗示。
  • 不把 AI 补绘结果直接标为高质量完成（必须经过审核标记）。
  • 不为了增加图层数量而过度拆分；不需要独立运动的细节必须合并。

4. 角色与对象模型

4.1 角色

角色职责关键权限
原画提供者提供原画与动作意图（要做什么动作、哪些部位必须能独立动）提供/替换输入；确认分层计划
绑定师（主用户）导入 PSD、调整网格与变形器、做键形与物理、判定观感接受/修改/驳回规格；执行观感签核
审核人判定补绘是否可接受、观感是否像原画通过/驳回补绘与观感

说明：本产品不设「自动发布」角色。任何进入成品目录的动作都必须有人签核。

4.2 核心对象

对象定义关键属性
作品（Model）一次任务的全部产物画布尺寸、DPR、状态、证据清单
部件（Part）一个可独立运动或可独立显隐的绘图单元名称、所属分组、遮挡序、是否需补绘、审核状态
网格规格（MeshSpec）某部件的顶点与三角形目标顶点数、三角形数、覆盖率、外框比
变形器（Deformer）装载部件或子变形器的容器类型（warp/rotation）、父子关系、控制目标
参数（Parameter）驱动形变的自变量ID、范围、默认值、关键形状列表
物理（Physics）由输入参数驱动的摆动输入/输出参数、摆动组、适用部件
证据（Evidence）某项断言的可复查依据等级、生成方式、是否人工签核

4.3 部件分层基准

拆分依据是运动能力与遮挡关系，不是颜色。下表为评估清单；实际拆分数量随角色而变， 但「必须独立」的一律不得合并。

分组评估部件默认处理
头部 · 发后发、侧发、前发、刘海、辫子、散发、发饰长发分段（2~3 段），刘海独立
头部 · 脸脸、耳、眉（左/右）、眼白、虹膜、瞳孔、高光、上下睫毛、鼻、嘴眼白与虹膜必须分离；高光可并入虹膜
躯干脖子、颈部阴影、躯干、腰脖子独立；胸/腰按服装分段
上肢上臂、前臂、手；袖口上臂/前臂必须按关节分离
下肢大腿、小腿、脚；袜、靴、靴口装饰大腿/小腿必须按关节分离
服装前片、后片、袖子、领口、领结、裙摆（前/后/左/右）、内衬、腰带、肩带裙摆必须分片；领口/袖口可作派生层
配件饰品、飘带、手持物、链条、耳饰会摆动的必须独立并可挂物理

5. 功能需求

FR-01

输入分析与分层计划

P0

让绑定师在动手切图之前就能判断「这套素材能不能支撑我要做的动作」。

触发
用户提交原画并确认开始。
处理规则
分析并记录：画布分辨率与色彩模式；角色完整轮廓；头/躯干/四肢位置； 头发·脸·五官·服装·配饰的结构；部件之间的前后遮挡关系；用户声明的预期动作； 哪些区域被遮挡需要补绘；哪些部位适合合并、哪些必须独立。
当原画为多视角设定图时，必须指定「以哪一视角为主视角」，其余视角仅作补绘参考， 不得混入同一画布。
结果与状态变化
输出分层计划：部件清单（名称、分组、遮挡序、是否需补绘）+ 动作需求映射 + 合并/独立判定及理由。计划通过后才允许进入分割。
例外
原画缺少必要部位（如手被完全遮挡且无法补绘）时，计划中必须标为 「缺失·不可补绘」，并说明该动作将无法实现；不得用占位图形冒充。
FR-02

部件分割与遮挡补绘

P0

产出既干净又能支撑运动的部件像素；被遮挡的部分要补出来，且补绘必须可追溯。

触发
分层计划被确认。
处理规则
按计划切出各部件；同一部件内的线稿、底色、阴影、高光按「是否需要独立控制」决定合并或分离—— 默认合并，只有需要单独变色/单独运动时才分离。
对下列区域执行补绘：头发遮挡的额头、侧发后方的脸缘、袖内手臂、衣服下方躯干、 裙摆下可能露出的腿、被遮挡的关节连接处。 补绘须匹配原图的线稿、色彩、光照、透视与材质。
结果与状态变化
每个补绘区域产生一条补绘记录：区域范围、补绘依据（哪一侧的对称/哪段连续线稿）、 状态（待审核 / 已审核 / 驳回）。 状态为 待审核 的补绘不得让作品进入「素材分层完成」。
例外
补绘与周围像素的线稿/明暗接不上时，该区域降级为 驳回 并保留原始空洞， 由绑定师决定是否接受「带空洞的部件」。
禁止项
不得把棋盘格图案当作透明；不得把纯白背景合并进角色部件；不得把未补绘的拆分图当作完成品。
FR-03

统一画布与透明坐标

P0

保证部件在 PSD 里回到原位，不因自动裁边而错位。

处理规则
所有部件使用同一画布尺寸与同一坐标原点；部件必须带真正的 Alpha 透明像素， 透明区不得是白色或棋盘格。
若为节省体积对部件做了裁切，必须记录偏移坐标（原画布坐标系下的左上角）， 并在构建 PSD 时按偏移复位。偏移量为 0 的部件也要显式记为 0，便于校验。
结果与状态变化
生成一张复位校验图：所有部件按偏移贴回画布后的合成结果，与原画逐像素比对； 差异必须在报告中标明位置与幅度。
例外
若某部件因裁切导致复位后与邻接部件出现缝隙或重叠，阻断交付并要求重新组装。
FR-04

导入用 PSD 构建

P0

产出一份「Cubism 一定吃得下」的 PSD。这是整个产品最关键的一次交接。

硬约束（任一不满足即导入失败或改色，全部来自官方）
  1. 保存格式必须是 PSD
  2. 色彩模式必须是 RGB
  3. 通道必须 8bit/channel
  4. 色彩配置必须 sRGB
  5. 不得有同名图层
  6. 不得使用图层蒙版
  7. 线稿与剪切蒙版必须合并
  8. 每组最底层图层作为纹理，故线稿层与填色层须预先合并
  9. 图层属性须能对应 Editor 的 Color blend
  10. Opacity 会生效，但 Fill 按 100% 输出

来源：Notes on PSD creation · Import PSDs

触发
部件分割与补绘全部通过审核。
处理规则
按 §4.3 的分组建立多层组结构（组可多层嵌套）。每个部件在组内是单一图层， 线稿与填色已合并。图层名唯一且稳定，直接使用部件名，不使用序号前缀之外的装饰性文字。
图层顺序即遮挡顺序：后排在下、前排在上，与编辑器里的 z 序一致。
参考层的处理（容易踩坑）
官方明确「PSD 中隐藏的图层与组也会被导入」。因此原图参考层不能直接放进导入用 PSD， 否则会被转成一个占满画布的 ArtMesh。参考图只能通过以下方式承载： ① 作为独立文件随包交付； ② 走「重新导入 → 仅注册 PSD、不添加 ArtMesh」的方式挂到项目里； ③ 作为「原图 / 模型导引图」使用。 白色背景参考层同理，不得作为普通图层进入导入用 PSD。
结果与状态变化
产出一份 PSD，以及一份图层清单：图层名、分组路径、画布偏移、像素数、遮挡序、对应部件。 图层清单是后续「导入是否完整」的比对基准。
例外
部件名在合并后出现重名（例如左右拆分后同名）时，必须自动加侧别后缀并同步更新图层清单； 不得静默丢弃其中一个。
FR-05

PSD 自检

P0

在交出去之前，自己先当一次 Cubism：能不能打开、层对不对、合出来像不像。

触发
PSD 构建完成。
处理规则
三项必查：① 重新打开 PSD，逐层读取并核对与图层清单一致（数量、名称、分组、尺寸、偏移）； ② 检查硬约束（格式/位深/色彩模式/同名/蒙版/Fill 与 Opacity）； ③ 把 PSD 各层按遮挡序合成，与原画比对。
结果与状态变化
自检通过的 PSD 才标记为 可导入；任一硬约束不通过则标记 不可导入 并阻断交付，同时列出具体违规项。
例外
合成差异可能来自补绘区域（原画中被遮挡，合成时露出来了）。报告必须区分 「补绘导致的合理差异」与「分割/组装错误导致的差异」。
FR-06

像素网格规格

P0

让绑定师知道每个部件该用多密的网格，并给出可直接核对的目标顶点集。

处理规则
为每个部件生成网格规格，并逐像素校验覆盖率：部件里每一个不透明像素都必须落在 某个三角形内，未覆盖像素数必须为 0。同时报告外框比（网格面积 ÷ 部件面积）， 作为「网格是否过松」的量化依据。
网格密度按部件规模自适应：大面积部件用较粗的初始格，轮廓与细节处细分到更小的格； 极小部件（如鼻尖）允许外框比偏高，但必须在报告中列出。
结果与状态变化
每个部件产出一条规格：顶点数、三角形数、覆盖率、外框比；以及整体统计。 规格用于三种用途：替换 Editor 自动网格时的目标、自检 Editor 网格密度是否够用、 自建编译链路的输入。
重点检查部位
脸轮廓、眼睛与睫毛、嘴部、细长发束、手指与关节、裙摆与飘带、饰品轮廓。
例外
轮廓里若存在「不属于任何部件但确实属于角色」的像素（色块接缝、外轮廓暗边）， 必须收进残差层并如实报告其占比，不得静默丢弃后再宣称 100% 覆盖。
FR-07

变形器层级规格

P0

把「每个部件该挂在哪、由谁带动」写清楚，避免绑定师从零设计层级。

处理规则
为每个部件指定：所属变形器、变形器类型（warp 用于形变，rotation 用于旋转）、 父子关系。层级必须满足：无环、每个部件恰好一个父级、关节段（上臂/前臂、大腿/小腿） 的父级是它的近端段。
必须明确每个变形器的控制目标（它想实现什么动作），而不是只给一个名字。
结果与状态变化
输出变形器树 + 每个部件的挂载关系。校验项：无环、无孤立部件、关节父子链完整。
禁止项
不得把变形器当成三维骨骼来描述或设计。Live2D 的核心是二维网格 + 变形器 + 参数 + 关键形状。
FR-08

参数与关键形状规格

P0

定义每个参数的作用、范围与关键形状，让「参数存在」和「参数有用」分开。

参数集合（P0）
ParamAngleX ParamAngleY ParamAngleZ ParamBodyAngleX ParamBodyAngleZ ParamEyeLOpen ParamEyeROpen ParamEyeBallX ParamEyeBallY ParamMouthOpenY ParamMouthForm ParamBrowLY ParamBrowRY ParamBreath
处理规则
每个参数必须声明：作用（驱动哪些部件产生什么变化）、取值范围、默认值、 关键形状列表（在哪些参数值上存在形状）。
范围须与角色的可动幅度一致（例如头部左右转不能超过脖子能承受的角度）， 不得给出会让部件穿模的范围。
结果与状态变化
输出参数表 + 每个参数的关键形状列表。 「参数已创建」不等于「参数已能驱动」：只有关键形状被实际制作、并在参数变化时观察到 预期形变，才能把该参数标为 已生效；否则保持 仅声明。
例外
某些参数在当前画布上无法产生可观测变化（例如没有对应的可动部件），必须标为 不可用 并说明原因，不得用空关键形状凑数。
FR-09

物理演算配置

P0

让摆动类部件在无手动运镜时也有自然的次级运动，且不会失控。

制作顺序（必须遵守）
① 后发 → ② 侧发与发梢 → ③ 飘带 → ④ 耳饰与链条 → ⑤ 裙摆与服装。
处理规则
先完成基础变形，再启用物理。每个摆动组必须声明输入参数与输出参数， 并绑定到具体的变形器/部件。摆动参数需与部件长度相关：越长的发束摆幅与延迟越大。
结果与状态变化
输出 physics3.json 与一份物理清单（组名、输入、输出、适用部件）。 物理配置文件属于运行时文件，可随包直接交付。
验收判据（可观测）
不得出现：持续抖动、部件漂浮、明显穿模、无法回归默认位置。 具体数值容差 TBD，由验收人按角色幅度确认； 判据先以「静置后收敛、回到默认参数后复原、极端参数下不穿模」三条为准。
FR-10

检测、验收与证据等级

P0

把「做过了」和「验证过了」分开，避免用一句「导出成功」掩盖能力缺口。

必测项
原始姿势合成、头部左右转、抬头低头、头部倾斜、眼球移动、眨眼、嘴部开合、表情切换、 身体倾斜、手臂运动、头发与饰品物理、裙摆与飘带运动。 每项输出结果 + 问题清单。
证据分级
E0 机器已验：可由程序复算（覆盖率、像素守恒、图层清单一致、硬约束校验、层级无环）。
E1 内核已验：模型能被官方内核加载，且参数变化产生预期形变（逐像素比对）。
E2 人工已签核：补绘可接受、观感像原画、物理手感自然。 只有 E2 由人给出，产品不得代签。
结果与状态变化
验收报告逐项列出：断言、等级、依据、结论。同一份报告里不得出现 「E2 未做但整体标为通过」。
例外
环境不具备官方内核时，E1 项必须标为 未验证·环境缺失， 不得因为「CI 全绿」推断为通过。
FR-11

交付物与作品状态机

P0

让任何人拿到产物就能判断它处在哪一步、还差什么。

交付物
① 导入用 PSD；② 图层清单与网格规格；③ 独立部件 PNG（带偏移）；④ 变形器/参数/物理规格； ⑤ physics3.json；⑥ 分层计划与补绘记录；⑦ 验收报告；⑧ 预览图。
可编辑工程（.cmo3）不在默认交付物内，见 §2。
作品状态机
已受理 → 已规划 → 已分割 → 已补绘待审 → 素材分层完成 → 已导入 → 绑定中 → 绑定完成。 每次跃迁必须有对应证据；缺少证据时停留在原状态并给出缺口清单。
两个完成态的定义
素材分层完成：PSD 自检通过 + 补绘全部为 已审核 + 网格规格覆盖率 100%。
绑定完成：E0 全部通过 + E1 全部通过 + E2 全部签核。
禁止项
不得把空图层模板、原图复制层、未补绘的拆分图、未经验证的 PSD 声称为完整可动的 Live2D 成品。 任何降级产出必须在产物中显式标注降级原因。

6. 共享规则

6.1 命名规则

  • 图层名 = 部件名，全局唯一；左右对称部件用统一后缀（_L / _R）。
  • 关节段命名固定为 upper_arm_* / forearm_* / thigh_* / shin_*， 便于父子链自动建立。
  • 同名冲突时自动加侧别或序号后缀，并同步写入图层清单；不允许静默覆盖。

6.2 坐标规则

  • 全作品统一画布，原点统一为左上角。
  • 裁切必须记录偏移；偏移为 0 也要记录。
  • 任何会改变部件位置的步骤，都必须重跑复位校验（FR-03）。

6.3 状态与证据的一致性

  • 一个状态的跃迁条件只有一个定义，散落在功能章节里的必须回到本节口径。
  • 「已审核」只能由审核人给出；系统只能置为「待审核」。
  • 报告里的每一条「通过」都必须挂一个证据等级；无等级即视为未验证。

6.4 降级与不可用

情形产品行为
补绘模型不可用保留空洞，标 缺失·不可补绘，并在计划中说明哪些动作无法实现
官方内核不可用E1 标 未验证·环境缺失，不得推断为通过
网格键形无法烘焙参数保持 仅声明，说明「参数存在但不驱动画面」
PSD 硬约束不满足标记 不可导入 并阻断交付，列出违规项

7. 开放问题

问题为什么现在定不了影响
目标画布尺寸与 DPI 是否强制 4096×5120 / 350dpi？ 参考图给出的是这一组值，但未确认是「本作品要求」还是「示例」。尺寸直接影响网格密度与纹理页数。 FR-03、FR-06
网格规格的默认密度取多少？ 密度是「形变精度」与「顶点数」的权衡，需要绑定师按动作幅度确认；当前只在 demo 上验证过一组参数。 FR-06
「绑定完成」是否要求物理手感也纳入签核？ 物理手感偏主观，是否单列一项 E2 需要与审核流程对齐。 FR-09、FR-10
是否接受自建 .moc3 编译作为「绑定完成」的合法路径？ 该路径能绕开 Editor 手工操作，但存在已知的内核加载不稳定问题；是否纳入 P1 取决于风险偏好。 §2、FR-08
